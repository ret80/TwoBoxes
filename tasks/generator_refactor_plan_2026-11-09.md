## 2. Разбор предложений документа

### Принято без изменений

| Пункт | Почему |
|---|---|
| А1 различимый результат анализа | `null` смешивает «нерешаемо» и «упёрлись в предохранитель»; на этом построено ложное «только обменом» |
| А2 единый обход | Убирает две копии BFS и двойной обход принятого кандидата |
| А3 причина отказа `place` | Тесное поле сейчас молча сжигает попытку |
| Б2 механики на маршруте | Главный источник 8.5 с и 6.3 с |
| Б3 шаг без записи путей | BFS не читает `paths`; это мусор на каждом ребре |
| Б4 числовые ключи | Поле ≤ 20×20 укладывается в число; строковый `join` — самая горячая аллокация |
| Б5 индекс порталов на уровне | `new PortalRule` на каждый ход убивает кэш парных клеток |
| Б6 прямой конструктор уровня | Убирает двойной `render` → `parse` и расхождение координат |
| Б8 не считать нечитаемое | `boxCells` не нужен в горячем обходе |
| В1 «механика нужна» | Тематический эпизод должен требовать механику, а не рисовать её |
| В3 `shortestCount` | Однозначность решения — реальная часть сложности |
| В4 `score` как цель, а не фильтр | Снимает невыполнимые профили и 400-попытные прогоны |
| Г1–Г6 структура, строители, реестр эффектов, `recipe.ts`, примитивы | Прямые нарушения SRP/OCP/DIP, подтверждены чтением кода |

### Принято с поправкой

1. **Б1 (обратная связь).** Идея верная, но одной обратной связи мало: причина
   отказа должна менять не только `walkMoves`, но и *способ* построения.
   Реализуем `Rejection` с `reason`/`delta` и цикл `build → accept → steer`,
   где `steer` подстраивает длину блуждания, квоту тупиков и порядок механик.
2. **Б7 (бюджет времени).** В ядре **нельзя** вводить wall-clock дедлайн:
   генерация детерминирована сидом, а сохранённые сиды игроков должны
   пересобираться в ту же карту. Вместо времени — **детерминированный бюджет
   работы** (число построений и суммарно исследованных состояний). Воркер
   получает предсказуемую стоимость, `rebuildEpisodeLevel` остаётся
   воспроизводимым. Wall-clock ограничение остаётся только в воркере как
   аварийный предохранитель.
3. **В2 (тупики).** Правильное направление, но это новый строитель с отдельной
   геометрией и риском для кривой. Делаем после стабилизации скорости, отдельным
   этапом, с проверкой хвоста эпизода.
4. **В5 (посаженный обмен).** Включаем только после А1/Б1, как builder
   `planted-swap`; случайный перебор оставляем запасным. Исследование 08.11 уже
   показало 50–85× продуктивность, но уровни короткие — нужен контроль длины.
5. **Порядок шагов документа.** Шаги 1–5 и 10 не меняют распределение `rng`;
   их делаем первыми и проверяем, что карты не поплыли. Шаги 6–9 меняют карты —
   выполняем вместе и фиксируем версию рецепта.

### Отклонено / отложено осознанно

- **Полный CSP-решатель** — не нужен: граф 48–118 состояний, выигрыш даёт
  сокращение числа построений.
- **Параллельная генерация в несколько воркеров** — после бюджета и обратной
  связи очередь перестаёт быть узким местом.
- **Новые веса сложности до В4** — сначала убираем противоречие профиля, потом
  калибруем.
- **Дублирование правил движения в «быстром» решателе** — запрещено: один
  `simulate` с флагом записи путей, а не вторая реализация правил.

## 3. Целевая структура (адаптирована к репозиторию)

```
src/core/generation/
├── rng.ts                     createRng, mixSeed, shuffle, pick
├── field/
│   ├── mask.ts                компоненты связности, largestComponent
│   ├── room.ts                createField (случайная комната)
│   └── render.ts              render, parse, createLevelFromMask
├── check/
│   ├── state.ts               числовой ключ состояния
│   ├── step.ts                переход без игровой обвязки
│   └── analyzer.ts            один BFS: shortest / analyze / firstMove
├── accept/
│   └── criteria.ts            Candidate + Acceptance + Rejection (reason/delta)
├── build/
│   ├── types.ts               LevelBuilder, BuildContext
│   ├── walk-builder.ts        блуждание «от решения», механики на маршруте
│   └── planted-swap.ts        посадка обмена
├── difficulty.ts              модель оценки (формулы сохраняются)
├── curve.ts                   профили эпизода как данные + политика допусков
├── recipe.ts                  сид ↔ рецепт, версия формата
├── solver.ts                  тонкие обёртки обратной совместимости
├── level-generator.ts         публичный фасад (~100 строк)
└── benchmark.test.ts          замеры (BENCH=1)
```

Швы: `Step` (переход), `Analysis` (различимый результат), `LevelBuilder`
(способ построения), `Acceptor` (причина отказа). Всё в `core`, без внешних
зависимостей.

## 5. Как проверяем

1. **Корректность:** `npm test` после каждого этапа; отдельно `move.test.ts`,
   `portal.test.ts`, `mechanics.test.ts`, `level-generator.test.ts`.
2. **Карты не поплыли:** на этапах 1–5 — отпечаток карт эпизодов до/после
   (FNV по строкам). Этапы 6+ меняют карты осознанно: версия рецепта повышается.
3. **Скорость:** `BENCH=1` до/после каждого этапа; цель — классический эпизод
   ≤ 0.7 с, эпизод переключателей ≤ 3 с, ловушек ≤ 3 с, без худшего уровня
   больше 1 с.
4. **Качество:** монотонность сложности, отсутствие уровня-обманки с механикой
   вне решения, доля успеха «только обменом» ≥ 9/10.
5. **Детерминизм:** `generateEpisode` = поштучная генерация; `rebuildEpisodeLevel`
   возвращает ту же карту.

## 6. Риски и решения

| Риск | Решение |
|---|---|
| Этапы 6+ меняют `rng` и карты | Версия рецепта; эпизоды перегенерируются; сохранённые сиды проверяются на принадлежность версии |
| Единый BFS меняет порядок обхода | Сохраняем порядок направлений и момент проверки победы; тесты на длину решения и replay |
| `stepBoxes` расходится с `moveBoxes` | Один `simulate`, флаг записи путей; тест «шаг = ход без путей» |
| Механики на маршруте делают уровень нерешаемым | Приёмка после раскладки; при отказе — следующий кандидат; счётчик отказов в бюджете |
| `score` как цель ломает монотонность | Выбор ближайшего из 4 кандидатов + проверка хвоста/головы эпизода |
| Wall-clock бюджет ломает воспроизводимость | В ядре — детерминированные единицы работы, время только в воркере |
